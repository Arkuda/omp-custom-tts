# Kokoro-ru для Oh My Pi

## Контекст

В пустом проекте `omp-custom-tts` нужно сделать устанавливаемое расширение Oh My Pi с локальным синтезом русской речи. Целевая среда проверена: Windows x64, `omp/19.0.1`, установлен Python 3.12 и `uv`. Использовать именно модель [zaakirio/kokoro-ru](https://huggingface.co/zaakirio/kokoro-ru), не подменять её английской Kokoro: русский G2P и веса нужны независимо друг от друга.
Пользователь выбрал ручную озвучку, экспорт WAV и отключаемую автоозвучку русских ответов ассистента. В `v19.0.1` `omp say` и встроенный вокализатор вызывают штатный worker с закрытым каталогом Phonon; публичный Extension API не регистрирует реализацию такого worker. Поэтому отдельное расширение, без форка OMP и без обещаний подменить `omp say`, `/speech` или встроенный `tts`.

## Подход

### 1. Локальный синтез и установка

- Создать `requirements.txt`: `ruaccent==1.5.8.3`, `misaki==0.9.4`, `phonemizer-fork==3.3.2` (не ставить одновременно `phonemizer`: общий import namespace), `espeakng-loader==0.2.4`, `num2words==0.5.14`, `onnxruntime==1.24.4`, `numpy==2.4.3`, `huggingface-hub==0.36.2`, `transformers==4.57.6`, `sentencepiece==0.2.3`, `python-crfsuite==0.9.12`, `razdel==0.5.0`, `markdown-it-py==4.0.0`. Для всех версий проверено наличие wheel для Windows x64/Python 3.12 или pure-Python wheel. Без torch, GPU и системного eSpeak.
- Добавить `setup.ps1` (запуск из каталога пакета или по абсолютному пути): если `%LOCALAPPDATA%\omp-kokoro-ru\.venv\Scripts\python.exe` отсутствует, создать venv через `uv venv --python 3.12 <venv>`; затем `uv pip install --python <venv>\Scripts\python.exe -r <package>\requirements.txt` и `<python.exe> -X utf8 <package>\kokoro_ru.py setup <dataRoot>`. Удалить старый `ready-v1` перед изменением venv; прервать при любом ненулевом коде. Пакет и пользовательская сессия OMP не меняются от Python setup. Если `LOCALAPPDATA`/`uv` недоступны, завершиться с точной причиной; Python ищет `uv` (у установленного `py.exe -3.12` интерпретатор не зарегистрирован). Не скачивать зависимости или модели при загрузке расширения.
- В `kokoro_ru.py` реализовать `setup`: через `huggingface_hub.snapshot_download(..., local_dir=...)` скачать `zaakirio/kokoro-ru@d649c57b239b18c4c384378127cbf01dba039bc1` в `<dataRoot>/kokoro/<revision>`, allowlist `ru_g2p.py`, `kokoro-config.json`, `espeak-data/**`, `onnx/model_quantized.onnx`, `onnx/model_dima_quantized.onnx`, `voices/sveta.bin`, `voices/masha.bin`, `voices/dima.bin`. Отдельным `snapshot_download` получить `ruaccent/accentuator@b78ae5ea1e62beaf138bed1865cd8c3b0b5ca855` с allowlist `dictionary/**`, `nn/nn_accent/**`, `nn/nn_omograph/turbo3.1/**`, `nn/nn_yo_homograph_resolver/**`, `nn/nn_stress_usage_predictor/**`, `koziev/**` в `Path(ruaccent.__file__).parent` внутри venv. Ровно там `RUAccent.load()` ищет их по умолчанию; вендорный `ru_g2p.py` не передаёт `workdir`, а `koziev` загрузчик всегда ищет относительно модуля. Не поставлять эти файлы в пакете; первый setup требует сети и скачивает примерно 1 ГБ данных.
- Импортировать `RuG2P` из каталога скачанной Kokoro-ru; его штатный конструктор подставляет лежащий рядом acute-aware `espeak-data` вместо штатного словаря. После скачивания запустить чистый дочерний `kokoro_ru.py worker <dataRoot>` с `HF_HUB_OFFLINE=1`, ответить setup ошибкой при ненулевом выходе/неуспешном синтезе любой из трёх озвучек фразы `Здравствуйте! Как ваши дела?` (временные файлы вне проекта). Только после smoke записать `<dataRoot>/ready-v1`. `setup` снимает старый маркер до скачивания, переиспользует скачанные файлы и может быть повторён после ошибки. Сам `worker` не проверяет маркер (его проверяет расширение); всегда принудительно включает `HF_HUB_OFFLINE=1` до загрузки зависимостей.
- Синтез по ONNX CPU: `sveta` (по умолчанию) и `masha` → `model_quantized.onnx`, `dima` → `model_dima_quantized.onnx`. Использовать upstream `RuG2P` и `kokoro-config.json` (его `vocab` совпадает с `config.json`, пробел в нём есть). Для фразы получить ID фонем, убрав OOV как в карточке, `input_ids` int64 `[1,n+2]` с нулями по краям; `style` float32 `[1,256]` из строки `len(ipa)-1` соответствующего `.bin` (`<f4`, reshape `[510,256]`); `speed` float32 `[1]`, значение 1.0. Брать waveform как `session.run(None, inputs)[0]`. PCM mono 24 kHz signed PCM16 через `wave`; преобразовать ограниченный `[-1,1]` float waveform в little-endian int16. Не записывать тишину как успешный результат при отсутствии речевых фонем.
- Прежде чем вызывать русский G2P, нормализовать пробелы внутри абзацев, сохранить границы абзацев/предложений. Делить по границам предложения (`[.!?…]` перед пробелом), длинное предложение разрезать по последнему пробелу до 160 Unicode code points, а слово без пробелов — на той же границе по code point. Если `len(ipa)>510`, рекурсивно разделить исходный фрагмент ближе к середине по пробелу, иначе по середине строки, и повторить G2P обеих половин; если даже один символ не влезает — ошибка, не усекать IPA. Пропускать фрагменты без речевых фонем (нет букв среди сохранённых IPA-символов), а если таких фрагментов нет во всём запросе, не выдавать WAV. При сборке писать фреймы последовательно в один WAV c 80 мс тишины **между** непустыми фрагментами; проверять, что waveform непустой, конечный и содержит ненулевой PCM.

### 2. Подключение к OMP и ручное управление

- Создать `package.json`: `"name":"omp-kokoro-ru"`, `"version":"0.1.0"`, `"type":"module"`, `"omp":{"extensions":["./index.ts"]}`, `"files":["index.ts","src","kokoro_ru.py","setup.ps1","requirements.txt"]`. `index.ts` — `export default function activate(pi: ExtensionAPI): void`, только type import из `@oh-my-pi/pi-coding-agent`; схемы через `const { z } = pi.zod` (`z.object`, `z.string`, `z.enum`, `.optional`). Не добавлять runtime npm-зависимостей. Установка из исходников — `omp plugin link .`, пробный запуск без регистрации — `omp --no-extensions --extension .`. Ресурсы Python искать относительно пакета, не `ctx.cwd`; `ctx.cwd` используется для пользовательского пути WAV.
- `src/runtime.ts` — один ленивый клиент Python и один активный запрос на экземпляр расширения. Runtime Windows x64; на других ОС оставить OMP запускающимся, ответить «Kokoro-ru: требуется Windows x64» только при запросе к расширению. До старта проверить `%LOCALAPPDATA%\omp-kokoro-ru\ready-v1` и наличие `.venv\Scripts\python.exe`; если нет — ошибка с абсолютным путем к `setup.ps1`. Модель загружать только на действительном запросе. Из встроенного OMP переиспользовать контракт Extension API; доступного API для Phonon-worker, встроенного Markdown-трансформера `SpeakableStream` или его плеера нет.
- Внутренний контракт `src/runtime.ts`: `type VoiceId = "sveta" | "masha" | "dima"`; `class KokoroRuntime` с `assertReady(): void`, `play(text: string, voice: VoiceId, kind: "manual" | "auto"): Promise<"played" | "skipped">`, `save(text: string, voice: VoiceId, target: string, signal?: AbortSignal): Promise<number>`, `stop(kind?: "manual" | "auto"): boolean`, `reset(): void`, `shutdown(): Promise<void>`. `play`/`save` синхронно проверяют условия и резервируют слот перед первым await (занятый `auto` возвращает обещание `"skipped"`); `stop()` отменяет любое проигрывание, `stop(kind)` — только указанный вид, `reset()` отменяет любой активный запрос, но не убивает простаивающий worker. `shutdown()` закрывает и простаивающий worker. `index.ts` проверяет и ловит и синхронные ошибки, и отклонение обещания.
- Клиент через `node:child_process.spawn` (`shell:false`, `windowsHide:true`) держит один процесс `<python.exe> -X utf8 -u <package>\kokoro_ru.py worker <dataRoot>`. stdin/stdout UTF-8 JSONL: запрос `{text:string, voice:"sveta"|"masha"|"dima", format:"plain"|"markdown", output_path:string}`; ответ ровно один `{ok:true,bytes:number}`, `{ok:true,skipped:true}` или `{ok:false,error:string}`. `skipped` только для Markdown без русского текста/речевых фонем. Один запрос в полёте, ID не нужен. Python сохраняет отдельный дескриптор для JSONL, направляет оставшийся stdout и diagnostics зависимостей в stderr до импортов. TS читает stdout построчно, stderr непрерывно с хвостом в 8 КиБ; ошибка запуска/обрыв/неожиданный JSON/таймаут (300 с на запрос) закрывают worker и отклоняют запрос. Никаких скрытых перезапусков текущего запроса; следующий запрос запускает новый worker. В Python хранить G2P, активную `onnxruntime.InferenceSession` и загруженные style packs между запросами; при смене checkpoint заменить сессию, а при смене `sveta`↔`masha` оставить общую базовую. EOF stdin останавливает worker.
- Для проигрывания worker пишет во временный каталог `mkdtemp` из `node:os.tmpdir()`. После успешного синтеза тем же venv, но отдельным дочерним Python-процессом `<python.exe> -X utf8 -c <константа> <wav>` вызвать `winsound.PlaySound(sys.argv[1], winsound.SND_FILENAME | winsound.SND_NODEFAULT)`. OMP не ждёт проигрывания в обработчике команд/событий; клиент отслеживает exit/error проигрывателя и удаляет WAV и каталог в `finally`, включая отмену. Ошибки команд через `ctx.ui.notify(..., "error")`, автоошибки также в `pi.logger.warn` без исходного текста. Не писать в stdout OMP. Прерывание на этапе синтеза убивает worker, на этапе проигрывания — только проигрыватель; следующие запросы используют оставшийся рабочий или новый worker. Не удалять временные файлы до выхода писавшего/проигрывающего процесса.
- `pi.registerCommand("say-ru", ...)`: `/say-ru <текст>` со `sveta`; `/say-ru --voice <sveta|masha|dima> <текст>` с явным голосом; остальная строка целиком как текст, не передавать его shell/argv. Валидировать разрешённый голос, непустой `.trim()` и длину `1..15000` JS UTF-16 units; ошибка аргументов выводит `Использование: /say-ru [--voice sveta|masha|dima] <текст>`. Для принятого запроса уведомление `Kokoro-ru: озвучиваю (<voice>)`, при завершении `Kokoro-ru: воспроизведение завершено`; при отмене не сообщать успех или ошибку.
- `pi.registerTool({name:"tts_ru", label:"Kokoro-ru TTS", approval:"write", loadMode:"essential", ...})`: точная схема `{text:string, output_path:string, voice_id?:"sveta"|"masha"|"dima"}`. Описание: локально синтезирует русский текст в PCM16 WAV, без проигрывания; `text` те же ограничения, `voice_id` по умолчанию `sveta`. Принимать только непустой путь с суффиксом `.wav` без учёта регистра; `path.resolve(ctx.cwd, output_path)`, родитель должен существовать. Синтезировать во временном каталоге внутри родителя; после успеха и проверки `signal` выполнить `rename` staging WAV в цель (с заменой существующего файла, как у штатного `tts`); при ошибке до rename исходный файл не менять. Всегда чистить staging, в том числе при abort. Ошибка окружения, синтеза или записи — throw с причиной (OMP показывает ошибку инструмента), а успех — `content:[{type:"text",text:"Kokoro-ru: сохранено <absolute path> (<voice>, <bytes> байт)"}]`, `details:{path,voiceId,bytes,sampleRate:24000}`.
- Общий admission: ручной запрос/экспорт при занятом слоте возвращает `Kokoro-ru: другой запрос уже выполняется`; новый авто-запрос при занятом слоте пропускается без уведомления. Отмену инструмента брать из `execute`-signal; `/speech-ru stop` отменяет только проигрывание с его синтезом, а не экспорт; `session_switch`, `session_clear`, `session_shutdown` отменяют текущий запрос любого вида. На shutdown закрыть/убить worker даже если он простаивает; не блокировать teardown дольше бюджета OMP.

### 3. Автоозвучка финальных ответов

- `pi.registerCommand("speech-ru", ...)`: `/speech-ru on`, `off`, `status`, `stop`; без аргументов то же, что `status`; иначе `Использование: /speech-ru on|off|status|stop`. Начальное состояние `off` в каждой интерактивной сессии, без записи в глобальные настройки; `session_switch` выключает автоозвучку, очищает кандидат и аудио. `on` проверяет готовность и разрешён только в `ctx.mode === "tui"` (в остальных режимах ответ `Kokoro-ru: автоозвучка доступна только в интерактивном OMP`). `off` отменяет текущую автоозвучку и очищает кандидат; ручные запросы не трогает. `stop` не меняет `on/off`. `on/off/status` подтверждают `Kokoro-ru: автоозвучка включена` или `Kokoro-ru: автоозвучка выключена`; `stop` подтверждает `Kokoro-ru: воспроизведение остановлено` или `Kokoro-ru: нет активного воспроизведения`. Автоозвучка всегда `sveta`; не включать и не менять штатную настройку `speech.enabled`; для параллельно включённой штатной озвучки пользователь сам выключает её через `speech.enabled: false`.
- `agent_start`: очистить свежий ответ/кандидат и отменить старое **автоматическое** проигрывание, не ручное. В `turn_end` запомнить ключ последнего свежего `assistant` сообщения `{timestamp,responseId}` (включая ошибки и tool-use) или сбросить при отсутствии assistant. `session_stop` только синхронно формирует кандидат: очистить старый, потребовать `on`, `ctx.mode === "tui"`, совпадение `event.session_id` с `ctx.sessionManager.getSessionId()`, неотменённый `event.signal`, свежий ключ из `turn_end`, `last_assistant_message.role === "assistant"`, `stopReason === "stop"`, отсутствие блоков `toolCall` и хотя бы один непустой `type:"text"`; никаких решений `continue`/`block`. Именно `session_stop` отсекает subagent-сессии. Кандидат содержит ключ и текст из `text` блоков по порядку, соединённых двумя переводами строки; думание, tool results и custom messages не читать. `agent_end`: при `willContinue`/`awaitingAsyncWork` сбросить кандидат и ничего не говорить. Иначе одноразово взять и очистить кандидат, сопоставить его ключ с последним assistant из `event.messages`, запустить фоновое `format:"markdown"` без ожидания и только если всё ещё `on`, TUI и есть слот. Не брать ответы из истории при отсутствии свежего кандидата; не повторять кандидат после проигрывания. При переходах сессии очистить обе метки.
- Для `format:"markdown"` использовать `MarkdownIt("commonmark").enable("table")`; обходить токены `inline` вне `table_open`/`table_close`. Собирать только дочерние `text` (видимый текст ссылок оставить; удалить `https?://`/`www.` URL до следующего пробела), `softbreak`/`hardbreak` переводить в пробел, между непустыми inline-блоками оставлять границы абзацев. Fence/indented code, inline code, таблицы, изображения, HTML-блоки и теги не читать. Отбросить блоки без букв `[А-Яа-яЁё]` после этой обработки, чтобы отдельные английские абзацы не звучали; фразы со смешанным текстом и русскими буквами оставить. Пустой результат — `skipped` без загрузки моделей Kokoro/RUAccent. Для авто ограничить вход первыми 15 000 UTF-16 units, не разрезая surrogate pair; ручная команда и `tts_ru` длинный ввод отклоняют.

## Проверка

1. **Чистая установка и ONNX.** Из `omp-custom-tts` в PowerShell: `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\setup.ps1`. Требуются Windows x64, OMP 19.0.1, `uv`, сеть к PyPI/HF и место под ~1 ГБ весов/словарей плюс venv. Ожидать exit 0, `ready-v1` и прохождение трёх WAV smoke в офлайн worker. Одним временным Python smoke (`python -X utf8 <script>`, без сохранения в пакете) запустить тот же worker, отправить JSONL для всех трёх голосов и длинного текста (`"Здесь проверяется озвучка русского предложения. " * 24`), после получить `ok` и `bytes` равен размеру файла. Через `wave` проверить `nchannels=1`, `sampwidth=2`, `framerate=24000`, ненулевые сэмплы и длинный WAV дольше короткого; WAV `masha`/`dima` не равны `sveta`. Затем `format:"markdown"` для `Only English.\n\n` + fenced code с кириллицей, кириллической таблицы и `<https://example.com>` → `skipped:true`, файла нет. Пунктуация `!!!` при `format:"plain"` → `ok:false`, после неё валидный повторный запрос в том же процессе успешен. Закрыть stdin, выход 0.
2. **Регистрация и ручной playback.** Из корня пакета временным Python RPC-драйвером запустить `omp --no-session --no-tools --no-lsp --no-extensions --extension . --mode rpc` (OMP использует манифест каталога без глобальной установки). JSONL `get_available_commands` → найдены `say-ru` и `speech-ru`; `prompt /speech-ru status` → выключена; `prompt /speech-ru on` → отказ строго про интерактивный режим; `prompt /say-ru --voice missing Привет` → подсказка использования. С акустикой на машине `prompt /say-ru --voice dima Привет, мир!` → уведомление `озвучиваю (dima)` и затем `воспроизведение завершено`, без не-JSON строк в stdout. Длинный `/say-ru` + `/speech-ru stop` сразу после уведомления начала → подтверждение остановки, без уведомления об успешном завершении; затем короткий запрос снова проигрывается. Закрытие stdin → exit 0.
3. **Экспорт через инструмент.** В пустом временном cwd запустить `omp --no-session --no-lsp --no-extensions --extension <absolute-package-directory> --tools tts_ru --approval-mode yolo --mode json -p "Вызови ровно один раз инструмент tts_ru с text: Привет, мир!; voice_id: masha; output_path: smoke.WAV. Не используй другие инструменты."` с уже настроенной моделью OMP. Наблюдать реальный tool result `Kokoro-ru: сохранено ... (masha, ... байт)` и проверить PCM16/24 кГц и ненулевое аудио в `smoke.WAV`. Для проверки сохранения прежнего файла повторить с `text: !!!` и тем же WAV: tool error, размер и SHA-256 файла неизменны. Если OMP не имеет рабочей настроенной модели, не вводить вымышленные ключи: выполнить проверки worker/RPC и явно отметить, что модельный вызов инструмента не проверен.
4. **Автоозвучка в настоящем TUI.** В пустом временном cwd создать временный оверлей `smoke.yml` со значением `speech: {enabled: false}`. Запустить `omp --no-session --no-lsp --no-extensions --extension <absolute-package-directory> --config smoke.yml --tools tts_ru --approval-mode yolo` на Windows с настроенной моделью. До `/speech-ru on` ответ `Ответь одной фразой: «Привет, мир!»` не запускает плеер. После `/speech-ru on` запросить `Ответь двумя русскими предложениями: «Привет, мир! Проверка русской речи завершена.»` → после финального ответа один запуск проигрывателя и два предложения; TUI остаётся отзывчивым. `Reply exactly: Hello from Windows.` → плеера нет. Запросить `Вызови tts_ru с text: Это тест экспорта и output_path: auto-test.wav. После результата ответь только: Это итоговый ответ.`: экспорт сам не играет, озвучивается только финальный текст. После `/speech-ru off` повторный русский ответ не играет; после нового включения проверить `/speech-ru stop` на длинном ответе и закрытие OMP без осиротевших `kokoro_ru.py worker`/`winsound` процессов. При отсутствии доступа к акустике наблюдать создание/выход отдельного процесса `winsound` и подтвердить WAV через worker, не заявлять, что звук прослушан.

## Допущения и действия при сбоях

- Поддержка Windows x64, CPU, три встроенных голоса; автоозвучка по явному выбору в текущей сессии, включение не переживает её смену или перезапуск. Никакой зависимости от штатного английского движка.
- При ошибке загрузки ONNX DLL WinError 126 проверить, что venv действительно x64 Python 3.12; если bitness совпадает и не хватает системного VC++ runtime, сообщить про Microsoft Visual C++ Redistributable x64 и не менять системные пакеты без пользователя. При обрыве сетевой загрузки повторить `setup.ps1` с тем же каталогом кеша; не переключаться на другую модель/ревизию.
